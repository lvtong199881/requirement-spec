# 编排协议（主流程专用）

主流程是**编排者**：不写任何阶段产物，只做六件事——向用户提问、组装任务包、校验产物、判定评审意见、处理停点、执行 commit。阶段 1–8 各由一个独立子 agent 执行。

## 为什么要这么耦合

子 agent 之间不共享上下文：它看不到主流程的推演，也看不到上一个 agent 的对话。**能跨 agent 传递的只有文件**。所以约定是硬的：

- 上游产物必须落成文件，且按统一编号（REQ / AC / CR / OOS）标识。
- 下游只读任务包指定的文件，读不到就报阻塞，不去猜。
- 主流程不在任务包里写结论性判断（“已经完成”“应该没问题”会让下游顺着走）。

## 起 agent

```text
subagent(
  description: "<角色名>｜<需求标识>",      # 会话列表显示名
  prompt: <任务包全文>                       # 第一行也是「<角色名>｜<需求标识>」
)
```

- **一律 `subagent`，不用 `subagent_fork`**：全新上下文是独立性的前提。
- **一个角色一个实例**：同一角色在同一需求内复用（评审复审、开发修缺陷、需求 agent 按回答定稿），用 `send_message` 续跑；换需求才重起。**“复用”就是不再调 `subagent`**：复审不是新评审，别因为“又到了评审环节”就再起一个——起多少 agent 看角色数，不看环节数。
- **跨角色绝不复用**：开发、评审、测试永远是三个实例；有界面变化时验收也是独立实例。
- 起之前先读该阶段的 `README.md`（角色卡）和 `templates.md`（准出清单），任务包里注明让它自己先读角色卡。

## 任务包结构

固定五段，缺一段就补，不要临场发明格式。**【输入】里的文件清单必须逐个对应 SKILL.md「阶段 I/O 契约」里该阶段「读」列出的项**，不多不少；【任务】里的产物路径必须对应「写」列。

```text
<角色名>｜<需求标识>

【身份】你是 <角色名>，相当于 <同事工程师 / 产品经理 / QA …>。先读 <角色卡路径> 再动手。

【任务】<一句话说清这一阶段要产出什么，以及准出标准在哪>
  - 做法：<该阶段 README 路径>
  - 准出清单：<该阶段 templates.md 路径>
  - 产物写到：docs/requirements/<需求标识>/<文件名>

【输入】只读这些，不要读别的：
  - <上游产物路径 1>
  - <上游产物路径 2>
  - <相关源码/目录>
  - 项目规范：<AGENTS.md 路径>

【硬约束】
  - <本阶段的禁止项，从角色卡的“不做什么”摘>
  - 只写本阶段产物，不改上游文档；发现上游有错写进回执的「阻塞与上游问题」
  - 不执行不可逆动作（commit / push / 发布 / 删数据）；需要时写进回执交主流程
  - 判断拿不准时写进回执的「待决策」，不要自己拍板

【回执】结束后用 send_message 回一段，格式见下
```

### 各阶段任务包的输入清单（照抄）

| 阶段 | 【输入】写这些 | 【任务】产物写这里 |
| --- | --- | --- |
| 1 | 用户原始需求原文（已转述）、`AGENTS.md`、项目目录结构、`docs/ui-screenshots/`、check 输出 | `需求卡片.md`、`PRD.md`、`待提问清单.md` |
| 2 | `PRD.md`、`需求卡片.md`、项目设计规范与主题、`docs/ui-screenshots/<页面标识>/`、check 输出 | 临时目录：`design-spec.json`、`html/`、PNG、按需 `use-figma.js` |
| 3 | `PRD.md`、`需求卡片.md`、`设计说明.md`、现有代码结构与依赖清单 | `技术方案.md` |
| 4 | `技术方案.md`、`设计说明.md`、`AGENTS.md`、相关源码目录 | 项目内源码 / 资源 / **单元测试**；`技术方案.md` 开发内容状态列；**debug 包 + 版本 + 安装命令** |
| 5a | `PRD.md`、`技术方案.md`、改动文件清单 + `git diff`、`AGENTS.md` | `代码评审报告.md` |
| 5c | 判定结果、`代码评审报告.md` 的问题清单 | 项目内源码修正；改了代码就**重新构建 debug 包**并更新版本 |
| 5d（续跑） | 修正后的 diff + 本轮要闭环的问题编号 | `代码评审报告.md` 的「复审结果」节 |
| 6 | **完整 `PRD.md`**（全篇，不要节选）、`技术方案.md`、debug 包路径 + 版本 + 安装运行命令、测试账号与数据 | `测试报告.md`、`docs/ui-screenshots/` |
| 7 | `PRD.md`、`需求卡片.md`、`设计说明.md`、`figma-import/` 或线上 Figma 稿、`docs/ui-screenshots/`、debug 包路径与安装方式 | `验收文档.md`（不含「交付说明」） |
| 8 | `PRD.md`、`测试报告.md`、`验收文档.md` | `复盘记录.md` |

### 不该出现在任务包里的东西

- 主流程的自评和推演（“我发现这个方案可行”“应该能通过”）。
- **源码 / 源码目录 / `git diff` / `代码评审报告.md` 给测试 agent**——它是黑盒 QA，只面对 app 与 PRD。
- `测试报告.md`、验收结论给设计、开发或评审 agent（会污染视角）。
- 源码给验收 agent（它的职责是不看代码）。
- **节选过的 PRD 给测试 agent**——必须给全篇，否则覆盖缺口无从判断。
- “上一轮你做得不错”这类评价——返工时只给缺口清单。

## 回执格式

```text
【回执】<角色名>｜<需求标识>
状态：完成 / 部分完成 / 阻塞
产物：<写出的文件路径列表>
自验：<本地跑了什么、结论是什么；没跑就写“未验证”及原因>
待决策：<需要主流程或用户拍板的点，没有写“无”>
阻塞与上游问题：<上游产物缺什么、错什么，没有写“无”>
```

收到回执后的动作：

1. 产物在 `状态=完成` 前一律不信，自己去读文件核对是否存在、是否为空壳。
2. 按 `templates.md` 的准出清单逐项校验，**逐项写结论**进编排记录。
3. 有缺口就把缺口清单（只列缺口，不列表扬）发回**同一个** agent 返工。
4. `状态=阻塞` 时判断是上游问题（退回对应 agent）、环境问题（按硬阻塞停下问用户）还是信息缺失（按关键分叉问用户）。

## 校验与返工

| 情况 | 动作 |
| --- | --- |
| 产物缺失或明显空壳 | 立即返工同一 agent，不自己补写 |
| 准出清单有未达标项 | 缺口清单发回，逐条对应到清单项 |
| 同一阶段连续三次返工不达标 | 停下，报告缺口与已尝试方向，请用户决策 |
| agent 报错退出或两次未产出可用产物 | 可换新实例重试一次（任务包不变）；仍失败按硬阻塞处理 |
| 上游文档有错导致本阶段做不下去 | 退回到产出该文档的 agent 修，不就地绕过 |

**主流程不得顶替执行**：任何阶段起不来 agent 时，不自己写 PRD、设计说明、技术方案、代码、测试报告或验收文档，按硬阻塞向用户报告。

## 评审阶段的特殊约定

评审是唯一需要**跨三个角色**的阶段，顺序固定：

1. 起**评审 agent**（`subagent`，全新上下文），给代码改动范围、技术方案、项目规范，不给主流程自评。
2. 收分级问题清单后，主流程**逐条判定**：已修复 / 不修 / 误报 / 待决策；不采纳要写理由。判定记录进编排记录。
3. 阻断和应修项发给**开发 agent**（`send_message` 续用开发阶段的实例）修正。
4. 修完用 `send_message` 请**同一个评审 agent** 复审改动点（**不新起实例**），不能自己宣布修好了。复审只判定本轮要闭环的问题编号，不重开评审、不重新提意见。
5. 复审通过或只剩建议项，才允许请求用户批准、进入阶段 6。

**阶段 5 总共只起两个 agent**：开发实例（阶段 4 起的，续跑）+ 评审实例（5a 起的，5d 续跑）。复审新起实例是典型错法——新实例没有首次评审的上下文，会把复审当首次评审重做，问题清单只增不减，永远走不到“只剩建议项”。5c / 5d 最多循环三轮，超过按返工超限停下报告。

测试或验收阶段改到代码时，回到第 3–4 步：**开发实例和评审实例都还是原来那两个**，继续 `send_message` 续跑，并把受影响路径写进测试报告的「变更后补充测试」。复审任务包的措辞见 [../5-review/README.md](../5-review/README.md) 的「复审任务包」。

## 阶段 I/O 契约

每个阶段的输入输出都写死在文件层面，主流程照契约组装任务包，执行 agent 只读契约里的输入、只写契约里的输出。

### 三条硬性规则

1. **一列一写者**：除三处例外，每份产物只有唯一的写者，写者之外只能读。三处例外是 `技术方案.md` 的「开发内容」状态列（归开发 agent 边做边更新）、`验收文档.md` 的「交付说明」节（归主流程）、`设计说明.md` 的「Figma 链接」列（归档上传后由主流程回填，因为设计 agent 起不了上传）。
2. **刻意不给的输入**：验收 agent 不给源码、改动范围、`测试报告.md`、主流程结论——拿到就会顺着测试结论验收，独立复核失效。**测试 agent 不给源码、`git diff`、`代码评审报告.md`**——它是黑盒 QA，只面对 app 和 PRD；同时 PRD 必须给**全篇**，节选会造成覆盖缺口。评审 agent 不给主流程自评、不给测试报告。设计 agent 不给技术方案。开发 agent 首次开发给不到评审结论。
3. **归档是主流程的落盘动作**：把临时目录的设计源移进 `figma-import/`、`design-images/` 并上传 Figma，是编排副作用不是代写产物；上传后的链接回填由主流程写入 `设计说明.md` 的 Figma 链接列——这是唯一例外，因为设计 agent 起不了 Figma 上传。

### 四条职责边界（容易搞混的）

| 事项 | 归谁 | 说明 |
| --- | --- | --- |
| 写并跑**单元测试** | 开发 agent | 测试 agent 拿不到源码，做不了；且 UT 是“写的人自己保证正确性”的一部分 |
| **构建 debug 包** | 开发 agent | 开发完成时出包并登记版本与安装命令；阶段 5 改到代码就重新出包 |
| **UI / 集成 / 主流程实跑** | 测试 agent | 黑盒执行，只看 app 行为 |
| **日志埋点校验** | 测试 agent | 按 PRD 的监测指标逐条核对，运行时读日志即可，不需要源码 |

### 输入缺失时

| 情况 | 动作 |
| --- | --- |
| 必需输入缺失或只有空壳 | 回执报阻塞，不许猜、不许自己造 |
| 可选输入缺失（如截图库里没有该老页面） | 按该阶段 README 的降级方式继续，在产物里写明降级原因 |
| 上游产物有错 | 写进回执的「阻塞与上游问题」，主流程退回产出它的 agent，不就地绕过 |


## 按需阶段：复盘（阶段 8）

用户要求，或需要用 PRD 的监测指标回看实际效果时才做。起复盘 agent，输入是 PRD 的监测指标、测试报告的日志校验结果、验收文档；输出 `复盘记录.md`，只写结论和建议，不改任何已有产物。

## 遥测（主流程的阶段边界动作）

阶段耗时、返工、评审判定、缺陷来源这些执行数据散在各需求的 `编排记录.md` 里，跨需求跨人无法聚合。所以主流程在阶段边界多打一行脚本，让数据能回答「团队用这个 skill 的效率如何、该改哪一段」。

**三条铁律**：

1. **只读侧信道**：数据只从流程流出，绝不回灌。遥测结果不写进任务包、不出现在给子 agent 的任何材料里——子 agent 知道自己在被度量，独立性就失效了。
2. **失败不影响主流程**：写入类命令永远退出码 0。存储不可写、脚本不存在，都只告警到 stderr，主流程继续跑，不因此停下问用户。
3. **不替代编排记录**：`编排记录.md` 是给人看的审计留痕，照旧写；遥测是给机器算的，两者都要有。

**执行时机**（脚本自己算耗时，主流程不做时间运算）：

| 时机 | 命令 |
| --- | --- |
| 受理需求、Figma check 之后 | `node assets/telemetry.js init --req <需求标识> --mode <主动/自动> --tier <档位>` → 打印 run_id，记下来 |
| 发出 `subagent` 之前 | `node assets/telemetry.js stage-start --run <run_id> --stage <1/2/3/4/5a/5c/5d/6/7/8> --role <角色名>` |
| 收到回执并校验之后 | `node assets/telemetry.js stage-end --run <run_id> --stage <同上> --status <完成/部分完成/阻塞> --rework <次数>` |
| 发回缺口清单时 | `node assets/telemetry.js rework --run <run_id> --stage <N> --round <轮次> --gaps "缺口1,缺口2"` |
| 逐条判定评审意见后 | `node assets/telemetry.js issue --run <run_id> --id CR-1 --level <阻断/应修/建议> --verdict <已修复/不修/误报/待决策>` |
| 复审结论出来时 | `node assets/telemetry.js recheck --run <run_id> --round <轮次> --result <通过/仍有阻断>` |
| 测试/验收报缺陷时 | `node assets/telemetry.js defect --run <run_id> --source <6/7> --severity <严重/一般/轻微> --introduced <yes/no> [--out_of_scope yes]` |
| 任何停点 | `node assets/telemetry.js stop --run <run_id> --type <澄清/关键分叉/不可逆动作/硬阻塞/返工超限> [--wait <等待毫秒>]` |
| 发现独立性被破坏 | `node assets/telemetry.js violation --run <run_id> --type <主流程代写产物/复审新起实例/给了源码/PRD 节选> --stage <N>` |
| 流程跑不下去了 | `node assets/telemetry.js abort --run <run_id> --reason <额度耗尽/子agent失败/用户放弃/环境错误/其它>` |
| 交付或中止时 | `node assets/telemetry.js close --run <run_id> --result <验收通过/带待决策/中止> --agents <起用数>` |

脚本路径写成 skill 目录下的 `assets/telemetry.js`，不要假设工作目录。

**中断必须打点。** 额度耗尽（429）、子 agent 失败、用户放弃、环境错误导致流程跑不完时，记一条 `abort`。这条不能省：没有它，中断的需求既不出 `stage.end` 也不出 `run.end`，会在报告里**彻底隐形**——既不算成功也不算失败，等于从未发生，而 429 恰恰是最该被看见的失败模式。中断阶段脚本能从「起了但没收尾」的 `stage.start` 自己推断，所以 `--stage` 可以不传。

来不及打 `abort` 也没关系：`report` 会把「超过 30 分钟没有任何事件、又没有结束信号」的需求标为**静默中断**并单独告警。这类通常是 429 额度耗尽或进程被杀——主流程连记录的机会都没有，所以报告必须自己认出来。

**漏报了不用补打点**：`编排记录.md` 是主流程必写的，跑 `node assets/telemetry.js parse --path docs/requirements` 就能从里面的「阶段进度」「评审判定」「停点记录」三张表回填出事件（同一需求重复执行幂等，靠文件路径+修改时间去重）。回填数据的耗时和缺陷字段是空的，`report` 会显式给出 L1 覆盖率——覆盖率低就是提醒该把打点补回来，不是数据错了。

**数据落在哪**：`<仓库根>/docs/requirements/.telemetry/events.jsonl`，按 git 仓库维度存，和产物同源、能和需求目录与 commit sha 对齐。不在 git 仓库里时降级到 `~/.dsh/telemetry/requirement-spec/<目录名>/`。想让它退出版本控制，`.gitignore` 加一行 `docs/requirements/.telemetry/`。

**看数据**：`node assets/telemetry.js report`（加 `--json` 出机器可读；`--path` 指定仓库；跨仓库先在 `~/.dsh/telemetry/requirement-spec/config.json` 的 `scanPaths` 里配上根目录再用 `--all`）。

## 不适用本协议的情况

阶段 8 之外的单个文档修订（例如只改提交信息规范）不属于流程阶段，直接做，不用起 agent。判断标准：它是否改变某个阶段的产物、是否影响下一环的准出。
