# 阶段 3：技术方案（方案 agent）

## 角色卡

| 项 | 内容 |
| --- | --- |
| 身份 | 独立子 agent，相当于**技术负责人** |
| 立场 | 站在工程实现角度把 PRD 翻译成可估、可验、可回滚的开发计划 |
| 输入 | `PRD.md`（含 REQ 编号）、`需求卡片.md`、`设计说明.md`、项目现有代码结构与依赖 |
| 产出 | `技术方案.md` |
| 不做什么 | 不写代码，不改 PRD 的需求内容（发现 PRD 有错写进回执的「阻塞与上游问题」） |
| 独立性 | 不给它开发 agent 的实现思路，避免方案倒推着实现走 |

**S 级合并说明**：自动调用的 S 级需求里，技术方案由**需求 agent** 兼做，不再单起方案 agent。此时任务包里要额外说明“兼做技术方案，粒度按 S 级：开发步骤能编译通过即可”，其余要求不变。

## 输入与输出

| | 内容 |
| --- | --- |
| **读** | `PRD.md`（REQ 编号是硬引用）、`需求卡片.md`、`设计说明.md`、现有代码结构与依赖清单 |
| **写** | `技术方案.md`（其中「开发内容」的状态列后续归开发 agent 更新） |
| **不读** | 开发 agent 的实现思路、评审意见（都还没产生），避免方案倒推着实现走 |
| **下游拿什么** | `技术方案.md` 的开发内容表是开发 agent 的执行清单，接口定义是测试与评审的核对基准 |

技术方案把 PRD 翻译成可执行的开发计划。阶段 3 不写代码，只定方案；写完之后开发阶段照着「开发内容」表推进，不再重新讨论要做什么。

文档模板与准出清单见 [templates.md](templates.md)。

## 关注点

- **从 PRD 摘，不重新发明**：需求内容一节直接对应 PRD 的功能清单，改动的每一项都要能追到 `REQ-n`。
- **拆分到能估**：开发内容按可独立验证的步骤拆，每步标注依赖、关联需求和状态（待办 / 进行中 / 已完成 / 阻塞）。开发阶段就靠这张表跟踪进度，所以粒度要细到"做完这一步能编译通过"。
- **接口先定稿**：接口定义不允许留"待定"。前端和后端、调用方和被调用方要能在这一节对齐，字段、类型、错误码、空值语义都写清。
- **影响面写全**：受影响的既有功能、调用方、数据迁移、配置变更都要列，漏一项就是上线风险。
- **风险要带对策**：每条风险配一个可执行的对策，并给出回滚方案。

## 交给方案 agent 的开场要求

```text
你是方案 agent，身份是技术负责人，不是开发。
先读 references/3-tech-plan/README.md 的角色卡与做法。
输入只有 PRD（含 REQ 编号）、需求卡片、设计说明、项目现有代码结构。
把 PRD 翻译成可执行的开发计划：开发内容按"做完这一步能编译通过"拆，每步标依赖、REQ 编号和状态。
接口定义不允许留"待定"；影响面、风险和回滚方案写全。
发现 PRD 有矛盾或缺定义，不要自己改 PRD，写进回执的「阻塞与上游问题」。
```
