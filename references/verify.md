# 阶段 6-7：测试与验收

## 两个子 agent 的角色别混

| 角色 | 相当于 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 评审 agent（阶段 5） | 同事工程师 | 看代码和文档，提工程改进意见，修完复审改动点 | 不跑构建，不判断需求是否达成 |
| 验收 agent（验收前，有界面变化才起） | 产品经理 | 拿到可安装的 debug app，装到模拟器上亲手跑，按 PRD 的验收标准逐条核对是否真的达成 | 不看源码和改动范围，不构建，不评价代码风格，不提重构建议，不做无界面需求的验收 |

这是两个角色、两个实例：不要用同一个子 agent 兼，也不要把评审结论当验收结论。验收 agent 发现代码层面的问题，转给主流程按 [review.md](review.md) 处理，不要自己展开工程讨论。

## 测试

- 真实执行：构建、单元测试、UI 测试，并从用户视角跑一遍主流程。
- 证据形式：命令结果、截图、日志、关键输出片段。
- **日志校验**：按 PRD 的监测指标逐条校验日志和埋点是否按预期上报，覆盖触发时机和关键参数，结果写进测试报告的「日志校验」一节。
- **截图归档**：测试和验收阶段的真实界面截图必须按页面存进 `docs/ui-screenshots/<页面标识>/<状态>.png`，同名覆盖更新，并在测试报告和验收文档里引用路径。这些图既用于回归对比，也是后续需求设计阶段可复用的老页面图，不要只留在临时目录或对话里。**Figma 导出图不能进这个库**，它只代表实际界面。
- **设计稿核对**：验收时把阶段 2 的 Figma 稿与真实截图逐状态对照，差异写进验收文档的「设计实现偏差」，并判定是设计变更还是实现偏差。Figma 稿是长期设计源，**不因实现完成而删除**，也不要求像旧流程的 Mockup 那样被截图替换。稿子是 `use_figma` 出的还是 `generate_figma_design` 捕获的都要照此核对——捕获通道的图层更碎，对照时看像素和排版，不要纠结图层结构。**核对本身不花额度**：真实截图走本地截图，Figma 一侧用 `figma-shot.js` 从 `html/` 重新出图对照，不要用 `get_screenshot` 去取线上的图（那是计费工具）。
- **无界面需求**：用单元测试、集成测试或示例工程替代 UI 测试，截图改为关键输出证据（日志、示例输出、接口返回），并在验收文档里写明“不适用及原因”；这类需求不起验收 agent。
- 跑不了的项写进验收文档的“未验证”区并注明原因，不能省略。
- **范围外的缺陷只记录，不修改**：测试发现的与本需求无关的既有 bug 和体验问题，只写进测试报告的「范围外发现」，不要顺手修掉。判定只看这条——是不是本需求验收标准所必需，或是不是本需求引入的回归；都不是就不改。范围外的高风险问题停下来告知用户，但同样不自行修改。
- 验收逐条对照需求卡片和 PRD 的验收标准，不用“基本符合”这类模糊结论。
- 验收文档同时包含交付说明：完成了什么、怎么验证、还剩什么待决策，不单独产出交付说明。


## 验收 agent（验收前必做）

### 角色卡

| 项 | 内容 |
| --- | --- |
| 身份 | 独立子 agent，相当于**产品经理**，代表需求方来验收交付 |
| 立场 | 只关心需求有没有真的达成，以及用户视角能不能用 |
| 输入 | PRD 的验收标准（必要时加需求卡片）、**可安装的 debug app**（APK 或等价构建产物）及其版本、安装与运行方式、必要的测试账号和测试数据 |
| 产出 | 每条验收标准的达成结论与证据（截图、录屏、关键输出）、分级问题清单（阻断 / 应修 / 建议）、整体结论（通过 / 有保留 / 不通过） |
| 不做什么 | 不碰源码，不看代码改动范围，不构建、不跑单元测试，不评价代码风格，不提重构建议 |
| 独立性 | 不给源码、不给改动范围、不给测试报告和交付说明，也不给主流程的推演和自评；它只从验收标准和手里这个 app 判断 |

### 执行要求

验收前必须起验收 agent，**不分档位、不分调用方式**：S、M、L 和用户主动调用都一样。唯一例外是无界面需求——页面没有任何变化时 PM 也看不出东西，这时不起验收 agent。

- **适用范围**：界面上有用户能看到的变化（新页面、新控件、文案或状态变化等）就必起；纯无界面需求（接口、数据、后台逻辑、只改日志或性能）不起，在验收文档的复核一节写“不适用（无用户可见界面变化）”及原因，验证由测试报告兜底。
- **用 `subagent` 起（全新上下文，不要用 `subagent_fork`）**：用新的实例，不复用评审 agent 那个实例；任务里让它先读本文件的「验收 agent」一节再动手。
- **固定名字**：DSH 没有 `agent_type` / `task_name` / `nickname_candidates` 参数，角色靠文本体现：`description` 写 `验收 agent｜<需求名称>`，任务第一行也写「验收 agent｜<需求名称>」，方便在会话列表里认出它。
- **它拿到的是 app，不是工程**：debug app 由主流程负责构建（复用测试阶段的产物即可），把产物路径、版本和安装方式交给它。它不构建、不改代码、不看改动范围——那些是开发工程师的事。
- **要求它自己体验验收**：把 debug app 装到模拟器或设备上，以产品经理的视角打开 app 按 PRD 验收标准逐条走一遍，用截图、录屏或关键输出取证，不允许只读文档就下结论；顺带看边界与异常场景、运行日志是否按 PRD 的监测指标上报。
- **不评审代码**：它的产出是“需求有没有达成”，不是代码好不好。看到代码层面的问题只做记录并转交，不展开工程讨论。
- **范围外的问题同样只记录**：它发现的与本需求无关的既有 bug 和体验问题写进验收文档的「范围外发现」，不顺手修，也不要让主流程去修。
- **要求它给分级结论**：发现的每个问题写清位置、证据、级别（阻断 / 应修 / 建议）和影响范围。
- **收口方式**：复核发现的问题按 [review.md](review.md) 的分级处理，阻断和应修项必须修正，影响业务逻辑时回归测试并把结果补进测试报告。结论写进验收文档的「验收 agent 复核」一节。
- **替代不了用户验收**：验收 agent 只是交付前的独立验证，最终验收仍由用户确认。
- **跑不起来时先报阻塞**：没有可用模拟器或设备、装包失败、app 起不来时，把阻塞点报给主流程去修（该修的是工程侧）；确实无法解决时写明原因和替代验证方式，不允许退化成只读文档就下结论。
- **无法起验收 agent 时**：记录原因，改为按上面的清单逐项自查，并在验收文档里写明这次没有独立复核。

### 交给验收 agent 的开场要求

```text
你是验收 agent，身份是产品经理，代表需求方验收交付，不是开发也不是 code review。
你拿到的是可安装的 debug app（路径见任务），不给源码、不给改动范围：不要构建、不要读代码。
把 app 装到模拟器或设备上，按 PRD 的验收标准逐条亲手走一遍，用截图、录屏或关键输出取证。
发现代码层面的问题只记录并转交，不评价代码风格、不提重构建议。
逐条给出结论和证据，问题分级，最后给整体结论：通过 / 有保留 / 不通过。
不要参考主流程的自评结论。
```

## 追溯矩阵

验收文档里必须有一张追溯矩阵，把每条验收标准追到实现和测试：

| 需求编号 | 验收标准 | 实现位置 | 测试用例 | 结论 |
| --- | --- | --- | --- | --- |

- 追不到的条目写清原因（未实现 / 未覆盖 / 不适用），不能留空。
- 矩阵里每条验收标准都要有结论，含糊的结论不算通过。
