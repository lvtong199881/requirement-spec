# 阶段 7 模板与准出清单

本阶段产出验收相关文档。模板里的占位内容一律替换成真实内容，空标题不要留在最终产出里。

## 文档模板

验收和交付合并为同一环节。验收文档同时包含验收结论和交付说明，不再单独产出交付说明。

```markdown
# 验收文档：<需求名称>

## 追溯矩阵
（每条验收标准都要能追到实现和测试，追不到的写清原因）
| 需求编号 | 验收标准 | 实现位置 | 测试用例 | 结论 |
| --- | --- | --- | --- | --- |

## 验收标准逐条核对
| 编号 | 验收标准 | 结论 | 证据 |
| --- | --- | --- | --- |

## 偏差项
（与需求不一致的地方，写清差异和原因）

## 设计实现偏差
（把设计说明里的 Figma 稿与本次验收后的真实截图逐状态对照，只列有差异的项；每项判定是「设计变更」还是「实现偏差」，实现偏差要给出处理结论。Figma 稿未上传时，用 `figma-import/design-spec.json` 作为对照基准并注明）
| 页面 | 状态 | Figma 稿 | 真实截图 | 差异 | 判定 | 处理 |
| --- | --- | --- | --- | --- | --- | --- |

## 未验证项
| 项 | 原因 | 建议验证方式 |
| --- | --- | --- |

## 假设复核
（开发过程中用到的假设是否仍然成立）

## 范围外发现
（本次验收或复核发现的、与本次需求无关的既有 bug 和体验问题：只记录不修改，留给用户决定是否另开需求；没有就写“无”）

| 编号 | 位置 | 现象 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| OOS-ACC-1 | | | | |

（编号带阶段前缀：评审用 `OOS-REV-n`、测试用 `OOS-TST-n`、验收用 `OOS-ACC-n`。不加前缀的话，同一需求里的 `OOS-1` 会指向三个不同的问题。同一问题在多个阶段重复出现时写「同 OOS-REV-1」，不占新编号）

## 验收 agent 复核
（由验收 agent 完成，相当于产品经理，不由主流程自评；无界面需求写“不适用（无用户可见界面变化）”，没有执行时写明原因和替代方式）
| 项 | 内容 |
| --- | --- |
| 复核范围 | |
| 验收产物 | （本次验收装的 debug 包路径 / 版本，以及设备或模拟器；由开发 agent 构建，不是验收时从源码构建的） |
| 复核方式 | 验收 agent 安装 debug 包，独立跑一遍逐条体验验证 |
| 发现的问题 | |
| 复核结论 | 通过 / 有保留 / 不通过 |

## 交付说明
（完成了什么、怎么验证、还剩什么待决策。**本节由主流程写**，其余小节由验收 agent 写）

## 结论
（可交付 / 有条件可交付 / 不可交付）
```

## 准出检查清单：验收 → 完成
- 验收文档由验收 agent（独立子 agent）产出；只有「交付说明」一节由主流程写
- 追溯矩阵完整，每条验收标准都能追到实现位置和测试用例
- 有用户可见界面变化的需求，验收 agent 已执行并在验收文档留下结论；无界面需求写明了“不适用”及原因
- 验收 agent 没看源码、没构建、没评价代码风格
- 设计实现偏差已逐状态对照并判定（设计变更 / 实现偏差）
- 复核发现的阻断、应修项已闭环（由开发 agent 修、评审 agent 复审、测试 agent 回归）
- 每条验收标准有明确结论
- 截图库中该页面各状态的图已更新到本次验收后的真实界面
- 偏差和未验证项显式列出
- 待决策事项集中整理在验收文档中，并由主流程向用户汇总
- 交付说明已合并进验收文档，不再单独产出

（主流程校验通过才算本次流程结束；不达标把缺口清单发回同一个验收 agent 返工。最终“完成”仍由用户确认。）
