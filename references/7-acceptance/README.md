# 阶段 7：验收（验收 agent）

验收要回答的是「需求有没有真的达成」，不是「代码写得对不对」。有用户可见界面变化时，先起独立的**验收 agent** 亲手跑一遍，主流程再合并交付说明并交付给用户确认。

## 主流程在这个阶段做什么

验收 agent 产出验收结论，主流程只做三件事，不代写验收文档：

1. **准备 app**：从开发 agent 登记的交付产物里拿到 debug 包（阶段 4 构建、阶段 5 改到代码时重新出包，登记在 `技术方案.md` 的「交付产物」一节），把包路径、版本号、安装与启动方式写进任务包。主流程不自己构建。
2. **合并交付说明**：验收 agent 给的是「需求有没有达成」，交付说明（完成了什么、怎么验证、还剩什么待决策）由主流程写进验收文档的对应小节。
3. **汇总待决策**：把验收 agent 的偏差项、未验证项、范围外发现整理成待决策清单给用户。

## 输入与输出

| | 内容 |
| --- | --- |
| **读** | `PRD.md`（验收标准全篇）、`需求卡片.md`、`设计说明.md`、`figma-import/design-spec.json` 或线上 Figma 稿、`docs/ui-screenshots/`、debug 包路径 / 版本 / 安装与启动方式 |
| **写** | `验收文档.md`（除「交付说明」外的全部小节：追溯矩阵、逐条核对、偏差项、设计实现偏差、未验证项、假设复核、范围外发现、验收 agent 复核、结论）；`docs/ui-screenshots/` 的更新 |
| **刻意不读** | **源码、改动范围、`测试报告.md`、评审结论、主流程自评**——拿到就会顺着测试结论验收，独立复核失效（PRD 要给全篇，不是节选） |
| **不做的动作** | 不构建、不跑单元测试、不改代码、不评价代码风格 |
| **下游拿什么** | 验收结论 + 待决策清单；「交付说明」由主流程补，最终由用户确认完成 |

### 和评审 agent 的分工

两个角色、两个实例，不要用同一个子 agent 兼，也不要把评审结论当验收结论。

| 角色 | 相当于 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 评审 agent（阶段 5） | 同事工程师 | 看代码和文档，提工程改进意见，修完复审改动点 | 不跑构建，不判断需求是否达成 |
| 验收 agent（验收前，有界面变化才起） | 产品经理 | 拿到可安装的 debug 包（开发 agent 构建、测试阶段已验证过的同一个包或更新包），装到模拟器上亲手跑，按 PRD 的验收标准逐条核对是否真的达成 | 不看源码和改动范围，不构建，不评价代码风格，不提重构建议，不做无界面需求的验收 |

验收 agent 发现代码层面的问题，转给主流程按 [../5-review/README.md](../5-review/README.md) 处理，不要自己展开工程讨论。

## 验收要求

- **设计稿核对**：把阶段 2 的 Figma 稿与测试阶段归档的真实截图逐状态对照，差异写进验收文档的「设计实现偏差」，并判定是设计变更还是实现偏差。Figma 稿是长期设计源，**不因实现完成而删除**，也不要求像旧流程的 Mockup 那样被截图替换。稿子是 `use_figma` 出的还是 `generate_figma_design` 捕获的都要照此核对——捕获通道的图层更碎，对照时看像素和排版，不要纠结图层结构。**核对本身不花额度**：Figma 一侧用 `figma-shot.js` 从 `html/` 重新出图对照，不要用 `get_screenshot` 去取线上的图（那是计费工具）。Figma 稿未上传时，用 `figma-import/design-spec.json` 作为对照基准并注明。
- **截图对齐**：测试阶段归档的图要更新到本次验收后的真实界面，同名覆盖。
- **逐条核对**：对照需求卡片和 PRD 的验收标准逐条判定，不用"基本符合"这类模糊结论。
- **无界面需求**：验证由测试报告兜底，验收文档的复核一节写"不适用（无用户可见界面变化）"及原因。
- **交付说明合并进验收文档**：完成了什么、怎么验证、还剩什么待决策，不单独产出交付说明。这一节由主流程写，其余小节由验收 agent 写。
- **最终验收由用户确认**：验收 agent 只是交付前的独立验证，替代不了用户。

## 验收 agent（验收前必做）

### 角色卡

| 项 | 内容 |
| --- | --- |
| 身份 | 独立子 agent，相当于**产品经理**，代表需求方来验收交付 |
| 立场 | 只关心需求有没有真的达成，以及用户视角能不能用 |
| 输入 | **完整 PRD**（验收标准为主，功能清单与边界异常也要）、必要时加需求卡片、**可安装的 debug 包**（APK 或等价构建产物）及其版本、安装与运行方式、必要的测试账号和测试数据 |
| 产出 | 每条验收标准的达成结论与证据（截图、录屏、关键输出）、分级问题清单（阻断 / 应修 / 建议）、整体结论（通过 / 有保留 / 不通过） |
| 不做什么 | 不碰源码，不看代码改动范围，不构建、不跑单元测试，不评价代码风格，不提重构建议 |
| 独立性 | 不给源码、不给改动范围、不给测试报告和交付说明，也不给主流程的推演和自评；它只从验收标准和手里这个 app 判断 |

### 执行要求

验收前必须起验收 agent，**不分档位、不分调用方式**：S、M、L 和用户主动调用都一样。唯一例外是无界面需求——页面没有任何变化时 PM 也看不出东西，这时不起验收 agent。

- **适用范围**：界面上有用户能看到的变化（新页面、新控件、文案或状态变化等）就必起；纯无界面需求（接口、数据、后台逻辑、只改日志或性能）不起，在验收文档的复核一节写"不适用（无用户可见界面变化）"及原因，验证由测试报告兜底。
- **用 `subagent` 起（全新上下文，不要用 `subagent_fork`）**：用新的实例，不复用评审 agent 那个实例；任务里让它先读本文件的「验收 agent」一节再动手。
- **固定名字**：DSH 没有 `agent_type` / `task_name` / `nickname_candidates` 参数，角色靠文本体现：`description` 写 `验收 agent｜<需求名称>`，任务第一行也写「验收 agent｜<需求名称>」，方便在会话列表里认出它。
- **它拿到的是 app，不是工程**：debug 包由**开发 agent** 构建并登记，主流程把包路径、版本和安装方式交给验收 agent。它不构建、不改代码、不看改动范围——那些是开发工程师的事。
- **要求它自己体验验收**：把 debug 包装到模拟器或设备上，以产品经理的视角打开 app 按 PRD 验收标准逐条走一遍，用截图、录屏或关键输出取证，不允许只读文档就下结论；顺带看边界与异常场景、运行日志是否按 PRD 的监测指标上报。
- **debug 包从哪来**：由**开发 agent** 构建并登记（阶段 4 出包，阶段 5 或测试缺陷修复后重新出包），登记在 `技术方案.md` 的「交付产物」一节；测试阶段的报告里记录了它验证过的包版本。主流程只把包路径、版本和安装方式写进任务包，不自己构建。验收应优先用**测试验证过的最新包**，如果开发在测试之后又改过代码，必须重新出包并重测。
- **不评审代码**：它的产出是"需求有没有达成"，不是代码好不好。看到代码层面的问题只做记录并转交，不展开工程讨论。
- **范围外的问题同样只记录**：它发现的与本需求无关的既有 bug 和体验问题写进验收文档的「范围外发现」，不顺手修，也不要让主流程去修。
- **要求它给分级结论**：发现的每个问题写清位置、证据、级别（阻断 / 应修 / 建议）和影响范围。
- **收口方式**：复核发现的问题按 [../5-review/README.md](../5-review/README.md) 的分级处理，阻断和应修项必须修正，影响业务逻辑时回归测试并把结果补进测试报告。结论写进验收文档的「验收 agent 复核」一节。
- **替代不了用户验收**：验收 agent 只是交付前的独立验证，最终验收仍由用户确认。
- **跑不起来时先报阻塞**：没有可用模拟器或设备、装包失败、app 起不来时，把阻塞点报给主流程，由主流程转给开发 agent 修（该修的是工程侧）；确实无法解决时写明原因和替代验证方式，不允许退化成只读文档就下结论。
- **无法起验收 agent 时**：记录原因，改为按上面的清单逐项自查，并在验收文档里写明这次没有独立复核。

### 交给验收 agent 的开场要求

```text
你是验收 agent，身份是产品经理，代表需求方验收交付，不是开发也不是 code review。
先读 references/7-acceptance/README.md 的「验收 agent」一节再动手。
你拿到的是可安装的 debug 包（路径与版本见任务）和完整的 PRD，不给源码、不给改动范围、不给测试报告：不要构建、不要读代码。
把 app 装到模拟器或设备上，按 PRD 的验收标准逐条亲手走一遍，用截图、录屏或关键输出取证。
同时把 Figma 稿（或 figma-import/design-spec.json）与真实界面逐状态对照，差异写进「设计实现偏差」。
发现代码层面的问题只记录并转交，不评价代码风格、不提重构建议。
逐条给出结论和证据，问题分级，最后给整体结论：通过 / 有保留 / 不通过。
不要参考主流程的自评结论；「交付说明」一节由主流程写，你不用写。
```

## 追溯矩阵

验收文档里必须有一张追溯矩阵，把每条验收标准追到实现和测试：

| 需求编号 | 验收标准 | 实现位置 | 测试用例 | 结论 |
| --- | --- | --- | --- | --- |

- 追不到的条目写清原因（未实现 / 未覆盖 / 不适用），不能留空。
- 矩阵里每条验收标准都要有结论，含糊的结论不算通过。
