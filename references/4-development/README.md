# 阶段 4：开发（开发 agent）

## 角色卡

| 项 | 内容 |
| --- | --- |
| 身份 | 独立子 agent，相当于**工程师** |
| 立场 | 按技术方案和项目规范把功能实现出来，能编译、单元测试通过、能出可安装的包、状态可跟踪 |
| 输入 | `技术方案.md`（开发内容表）、`设计说明.md`、项目 `AGENTS.md` 与现有代码 |
| 产出 | 源码改动、**单元测试**、**debug 包（含版本与安装命令）**、变更说明（改动文件清单 + 对应 REQ 编号） |
| 不做什么 | 不自我评审、不下最终测试结论（UI / 集成 / 主流程实跑归测试 agent）、不 commit / push、不做验收判断 |
| 独立性 | 不给它评审 agent 的意见之外的自评；测试结论由测试 agent 出，它不能替自己宣布“验证通过” |

开发 agent 还承担**所有代码修正**：评审发现的阻断和应修项、测试发现的缺陷、验收阶段的实现偏差修正，都发回**同一个开发实例**用 `send_message` 续跑，不要每轮新起，否则它不记得自己写过什么。

## 单元测试与 debug 包归开发阶段

这两件事最容易和测试阶段扯不清，这里定死：

| 事项 | 归属 | 理由 |
| --- | --- | --- |
| 写并跑**单元测试** | **开发 agent** | 单元测试是“写代码的人保证每段逻辑对”的手段，属于实现的一部分；测试阶段拿不到源码，做不了 |
| **构建 debug 包** | **开发 agent** | 测试阶段是黑盒，不构建。开发完成时出包并登记版本与安装命令；阶段 5 每改到代码就重新出包 |
| UI / 集成 / 主流程实跑 | 测试 agent | 黑盒执行，只看 app 行为 |
| 日志埋点校验 | 测试 agent | 按 PRD 监测指标核对运行时日志，不需要源码 |

### 单元测试要求

- 按项目既有测试框架和约定写，**不引入新框架**（要引入按关键分叉停下确认）。
- 覆盖技术方案里每个开发步骤的核心逻辑与边界，不是为凑覆盖率写空壳断言。
- 必须真实跑通，回执里给命令与结果；跑不了的写原因，不许写“应该有测试”。
- 纯 UI 调整、纯文案改动等无逻辑可测的步骤，写明“无单元测试，理由：…”。

### debug 包要求

- 有用户可见界面变化时，必须产出可安装的包（APK 或等价产物）。
- 登记三样：**产物路径、版本号、安装与启动命令**，写进 `技术方案.md` 或回执，供阶段 6 测试和阶段 7 验收直接取用。
- 阶段 5 修正、测试缺陷修复后**必须重新出包并更新版本**，不允许让测试或验收跑旧包。

**提交动作归主流程**：开发 agent 只写代码和变更说明，不执行 commit / push。主流程按下面的规范拟提交信息、停下确认、再提交。S / M / L 任何档位都一样——commit 是不可逆动作，不交给子 agent。

## 输入与输出

| | 内容 |
| --- | --- |
| **读** | `技术方案.md`（开发内容表）、`设计说明.md`、`AGENTS.md`、相关源码目录（项目内） |
| **写** | 项目内的源码 / 资源 / **单元测试**；`技术方案.md` 的「开发内容」状态列（待办 / 进行中 / 已完成 / 阻塞）——**这是唯一的跨阶段写权限**；**debug 包 + 版本 + 安装命令** |
| **不读** | 评审意见（首次开发时还没产生）、测试报告、验收结论；不给它主流程的自评 |
| **下游拿什么** | 代码 + 单元测试结果 + **debug 包（路径 / 版本 / 安装命令）** + 回执里的变更说明（改动文件清单、REQ 映射、建议提交切分） |

开发阶段按技术方案实现，一边写一边更新技术方案「开发内容」表里每一步的状态。文档模板与准出清单见 [templates.md](templates.md)。

这一阶段最容易留下长期债的是提交信息：它会被 `git log`、`git blame`、release note 长期读取，格式错了事后只能重写历史，所以在 commit 之前就要定下来。下面这份是本仓库提交规范的唯一出处——但先判断目标项目有没有自己的规范，有就照它的写。**这套规范由主流程在提交时执行，开发 agent 不 commit，但要在变更说明里给出建议的提交切分方式。**

## 先判断用哪套规范

固定顺序，不要跳过第一步：

1. **目标项目自带规范优先**。按下面顺序找，找到哪套就照哪套写，**不要再套本文件的默认值**：
   - `CONTRIBUTING.md` 里的提交信息章节
   - `.gitmessage` / `.gitmessage.txt`
   - `commitlint.config.{js,cjs,mjs,ts}`、`.commitlintrc.*`（看 `type-enum` 与 `rules`）
   - `package.json` 里的 `commitlint`、`husky`、`simple-git-hooks` 配置
   - 最近 20 条 `git log` 的实际风格（团队实际习惯常与文档不一致，以实际为准）
2. **都没有才用兜底格式**：`<type>(<scope>): <description>`，即 Conventional Commits 1.0.0。

兜底的 type 取值：`feat` / `fix` / `docs` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert`。`update`、`change`、`modify`、`wip` 不是合法 type。

写法：`description` 祈使语气、小写开头、不加句号（中文同样适用——写「删除重复说明」而不是「删除了重复说明」）；`scope` 写受影响的模块或目录；一次提交只做一件事；正文写**为什么改**和**影响什么**，不复述 diff；破坏性变更在 type 后加 `!` 并在 footer 写 `BREAKING CHANGE:`。

判断把握不大时按第 1 步的实际风格写，不要自己发明新格式。

### type 怎么选

| type | 用途 |
| --- | --- |
| `feat` | 新增能力（规则、脚本、模板、参考文档） |
| `fix` | 修正错误（脚本行为、文档事实错误） |
| `docs` | 只改文档，不影响行为 |
| `refactor` | 重构，不改变外部行为 |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建或依赖变更 |
| `ci` | CI 配置 |
| `chore` | 杂项（不影响源码与测试） |
| `revert` | 回滚既有提交 |

### 示例

```
feat(figma): 支持多状态一次提交出稿
docs(readme): 删除流程表后重复的设计阶段说明
fix(capture): captureId 重复消费时给出明确报错

BREAKING CHANGE: 不再等阶段 2 才做授权，
调用方需要在进入阶段 1 前先跑 figma-auth.js check。
```

### 校验

不需要工具链：照上面的格式逐项自检即可——`type` 在允许列表内、有可选的 `(scope)`、冒号后有一个空格、描述行不超过 100 字符、不以句号结尾，破坏性变更要写 `!` 或 `BREAKING CHANGE:`。目标项目自己配了 commitlint 或其他校验时，按它的命令跑。

## 和「不可逆动作先问」配合

SKILL.md 规则 5 要求 commit/push 前停下确认。**确认的那一刻就要把拟用提交信息原文贴出来**，格式：

```
准备提交 N 个文件：
  <file1>
  <file2>

拟用提交信息：
  fix(capture): captureId 重复消费时给出明确报错

确认后执行 commit 并 push 到 <branch>。
```

用户能在提交发生前就改格式，而不是事后要求重写历史。不要先 commit 再解释格式。

## 一次需求通常对应多条提交

开发阶段按技术方案的开发内容表逐步推进，提交也应该按语义单元拆开，而不是攒到最后来一条 `feat: 实现整个需求`。每条提交对应一个或几个相邻步骤，各自能独立编译。测试、验收阶段改到代码时单独提交，并在信息里点明修的是哪条缺陷或哪条评审意见。

## 已在远端的错误提交

- **只有自己在用、没人基于它开发**：可以用 `git commit-tree` 逐条重建（保留作者与时间戳），再 `--force-with-lease` 推送。重建后核对 `git log --format="%T"` 的 tree hash 与原提交一致，证明只改了消息、没动内容。
- **已经有人在用**：不要 force push。由用户决定是补一条说明性提交还是接受现状。

## 交给开发 agent 的开场要求

```text
你是开发 agent，身份是工程师，不是评审也不是 QA。
先读 references/4-development/README.md 的角色卡与做法。
输入只有技术方案（开发内容表）、设计说明、项目 AGENTS.md 和现有代码。
按技术方案的顺序实现，每完成一步更新技术方案的开发内容状态（待办/进行中/已完成/阻塞）。
单元测试由你做：按项目既有框架写，覆盖核心逻辑和边界，真实跑通并把命令与结果写进回执。
debug 包也由你做：有界面变化时构建可安装的包，登记产物路径、版本号、安装与启动命令。
不要自我评审、不要下最终测试结论（UI/集成/实跑归测试 agent）、不要 commit 或 push——提交由主流程做。
变更说明里写清：改了哪些文件、每个文件对应哪条 REQ、建议拆成几条提交。
编译和单元测试都过了再回执；没过就写进「待决策」，不要留着半成品说完成。
```
