# 阶段 5：代码评审与修正（评审 agent）

## 角色卡

| 项 | 内容 |
| --- | --- |
| 身份 | 独立子 agent，相当于**同事工程师做 code review** |
| 立场 | 站在工程角度质疑这份改动可不可靠、好不好维护、合不合项目规范 |
| 输入 | 需求卡片和 PRD 的路径、技术方案、本次代码改动范围、项目 `AGENTS.md` 规范、需要它读的文档和代码位置 |
| 产出 | 分级问题清单（阻断 / 应修 / 建议），每条带位置、证据、风险、改法；复审时给出改动点是否闭环的结论 |
| 不做什么 | 不执行编译、静态检查或测试；不判断需求有没有达成；不代替产品验收 |
| 独立性 | 不给它主流程的自评和“已完成”结论，防止它顺着主流程的判断走 |
| 续跑方式 | 5a 用 `subagent` 起一次；5d 复审必须用 `send_message` 发回**同一个实例**，不新起 |

它是主流程的**外部视角**，不是主流程的分身：判定、修正、闭环由主流程和开发 agent 分工完成，它只负责提意见和复审。它和验收 agent 是两个角色，不要复用同一个实例，也不要把评审结论当验收结论。

## 三方的分工

评审是唯一跨三个角色的阶段，各管一段，不要混：

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 评审 agent | 读代码和文档，提分级问题清单，复审改动点 | 不跑构建、不写代码、不判需求是否达成 |
| 主流程 | 逐条判定意见（已修复 / 不修 / 误报 / 待决策），决定哪些发回修，记录理由 | 不自己写代码修，不自己评审 |
| 开发 agent | 按判定结果修正代码 | 不给自己判定“已修复”，等评审复审 |

**一个需求只有两个实例**：开发是阶段 4 起的同一个实例（用 `send_message` 续跑，它记得自己写过什么），评审是 5a 起的同一个实例（5d 复审同样用 `send_message` 续跑，它记得自己提过什么问题）。**5d 复审不要新起评审 agent**——新实例没有首次评审的上下文，不知道原来的问题是什么、判定过什么，只能重看一遍代码当"新评审"，于是问题清单越审越多、永不成环。这一阶段总共只起两个 agent，没有第三个。

## 输入与输出

本阶段分四步，每步的读写不同，任务包要按步组装：

| 步骤 | 谁 | 读 | 写 |
| --- | --- | --- | --- |
| 5a 评审 | 评审 agent | `PRD.md`、`技术方案.md`、改动文件清单 + `git diff`、`AGENTS.md` | `代码评审报告.md` 的问题清单与评审结论；**不写修正结果** |
| 5b 判定 | 主流程 | `代码评审报告.md` | `编排记录.md` 的「评审判定」表（判定 + 理由） |
| 5c 修正 | 开发 agent（阶段 4 的同一实例） | 判定结果 + 问题清单 | 项目内源码修正；回执里的修正说明 |
| 5d 复审 | 评审 agent（同一实例） | 修正后的 diff | `代码评审报告.md` 的「复审结果」节 |

刻意不给的输入：

- **评审 agent 不读**：`测试报告.md`（测试尚未开始）、主流程的自评、验收结论。
- **评审 agent 不跑**：构建、静态检查、单元测试——那是开发与测试阶段的职责。
- **开发 agent 不写** 评审报告，也不给自己判定「已修复」；修正结果由评审在 5d 确认。

## 评审协议

- **触发时机**：开发阶段结束时、测试开始之前。当前需求有代码改动就必须执行；没有代码改动则记录“不适用”及原因。
- **首次评审（5a）用 `subagent` 起（全新上下文，不要用 `subagent_fork`）**：评审交给独立子 agent，主流程不自评。只给它材料，不给结论——需求卡片和 PRD 的路径、技术方案、本次代码改动范围、项目 `AGENTS.md` 规范、让它先读本文件。不要给它“已经实现完成”这类自评，否则它会顺着主流程的判断走。
- **复审（5d）用 `send_message` 续跑，不新起 agent**：复审是同一实例的第二次发言，不是第二次评审。给它的是“修正后的 diff + 要复核对付的问题编号”，让它只回答“原问题是否解决、有没有引入新问题”，**不重新提一轮新意见**（新发现的范围外问题可记，但不进本轮闭环判定）。起新实例是错的做法：它没有首次评审的上下文，会把复审当首次评审重做，问题清单只增不减、永远走不到“只剩建议项”，阶段 5 就卡死了。
- **固定名字**：DSH 没有 `agent_type` / `task_name` / `nickname_candidates` 参数，角色靠文本体现：`description` 写 `评审 agent｜<需求名称>`，任务第一行也写「评审 agent｜<需求名称>」，方便在会话列表里认出它。
- **一个需求一个评审实例**：同一个需求从首次评审到修完复审都用**同一个实例**，保证它有上下文；换需求或换改动范围就重新起一个，不要把上一个需求的结论带过来。测试或验收阶段改到代码再复审时，同样用 `send_message` 续跑这个实例，不新起。
- **只审代码，不跑构建**：评审只看代码、文档和本次改动范围，不执行编译、静态检查或测试。跑构建和测试是开发、测试阶段的职责，评审环节不做。
- **评审范围**：当前需求的代码改动、相关调用方、接口、数据、文档和可测性（有没有测试入口、日志能不能校验），不扩散到无关模块。测试充分性不在本次范围，由测试阶段的准出清单把关。看到范围外的既有问题可以报出来，但只记录，不要求修改。
- **评审重点**：需求覆盖、正确性、边界与异常处理、安全与权限、数据兼容、可维护性、项目 `AGENTS.md` 规范。
- **问题分级**：至少区分“阻断”“应修”“建议”。每条问题写清位置、风险、改进意见。**不要写「处理决定」**——判定是主流程的职责，统一落 `编排记录.md` 的「评审判定」表。
- **主流程逐条判定**：评审 agent 会误报，也可能提出与项目约定不符的意见。每条意见都要判定“已修复 / 不修 / 误报 / 待决策”，不能无脑照改；不采纳要写理由。判定记录进 `编排记录.md` 的「评审判定」表。
- **修正由开发 agent 做**：判为“已修复”的条目发给同一个开发 agent 实例修正，主流程不自己改代码——否则又变成写代码的人自己评审。
- **必须修正**：范围**内**的“阻断”和“应修”问题直接修正。需要扩大范围、增加依赖、改架构或数据模型时，按关键分叉停下确认。
- **范围外的问题只记录，不修改**：判定只看一条——这个问题的修复是不是本需求验收标准所必需，或是不是本需求引入的回归。都不是（原本就存在、与本需求无关的 bug 或体验问题，哪怕就在本次改动的文件里、顺手就能修）就**只记录不改**，写进评审报告的「范围外发现」，说明位置、现象、影响和建议，留给用户决定要不要另开需求。范围外的高风险问题（数据丢失、安全、支付等）停下来告知用户，但同样不自行修改。
- **处理建议项**：低风险且能明显改善质量的直接修正；否则在评审报告中记录不修理由。
- **修正后复审**：阻断和应修项修完后，用 `send_message` 让**同一个评审 agent 实例**复审改动点（不新起），确认原问题已解决且未引入新问题，不能自己宣布修好了。复审只判定本轮要闭环的问题编号，不重开评审。
- **用户批准门槛**：存在未闭环的阻断或应修项时，不得请求用户批准，也不得进入测试；评审通过或只剩建议项时才请求用户批准。
- **修正后的验证**：开发 agent 修完后跑一次编译和相关单元测试确认没改坏，把结果写进回执；**改了代码就要重新构建 debug 包并更新版本**。修正影响业务逻辑的，把受影响的**业务路径**（用业务语言描述，不附 diff、不带评审结论）写进回执，由主流程转给测试阶段进必测清单。
- **测试开始后的改动**：测试、验收阶段凡改到代码（缺陷修复、评审复审修正、验收修正），必须回到评审环节让评审 agent 复审改动点，并把受影响路径写进测试报告的「变更后补充测试」。复审同样是 `send_message` 续跑阶段 5 那个评审实例——它是这一需求改动的长期评审人，测试期每一轮修正都找它。
- **闭环**：所有问题条目必须有明确结论；存在未解决阻断项时不得进入验收。

## 交给评审 agent 的开场要求

把下面几点写进给评审 agent 的任务里，其余信息由它自己从仓库读取：

```text
你是评审 agent，身份是同事工程师做 code review，不是产品验收。
先读 references/5-review/README.md 的角色卡与评审协议再动手。
评审这个需求本次的代码改动，按项目 AGENTS.md 的规范检查。
只读代码和仓库里的文档，不需要执行编译、静态检查或测试。
不判断需求有没有达成，那是验收 agent 的事。
逐条列出问题，写明位置、证据、风险和建议；需要修改的地方直接给出改法。
问题分级：阻断 / 应修 / 建议。范围外的既有问题单列「范围外发现」，只记录不要求修改。
不要参考主流程的自评结论；也不要在评审报告里写"已修复"，那由开发 agent 修、你在复审时确认。
```

## 复审任务包（5d，发给同一个评审实例）

复审不是重新评审，措辞要把它钉死在“只回答这几个编号”上。`send_message` 发回阶段 5a 那个评审实例，不用再写身份和角色卡（它已经读过）：

```text
【复审】<需求标识>

开发 agent 已按判定结果修正，现在复审本轮要闭环的问题：<CR-1、CR-3、CR-5>（逐条列出编号）。

【输入】只读这些：
  - <修正后的 diff 或改动文件清单>
  - 你自己上一轮写的 docs/requirements/<需求标识>/代码评审报告.md（看这些问题的原文）

【这一轮只做三件事】
  1. 逐条确认上面这些编号的问题是否真的解决了，给出「已闭环 / 未闭环 + 还差什么」。
  2. 看修正有没有引入新问题——只报阻断和应修级的新问题，并标为「复审新增」。
  3. 把结论写进 代码评审报告.md 的「复审结果」节。

【不要做】
  - 不要重新评审一遍代码，不要重提已经判定为不修 / 误报的条目。
  - 不要新提建议级意见（看到就记进「范围外发现」，不进本轮闭环判定）。
  - 不要跑构建和测试，也不要写代码。
```

复审通过（本轮编号全部闭环、无新增阻断或应修）就进入阶段 6；有未闭环就回到 5c 再修一轮，最多三轮后按返工超限停下报告。
