# 阶段 5 模板与准出清单

本阶段产出代码评审相关文档。模板里的占位内容一律替换成真实内容，空标题不要留在最终产出里。

## 文档模板

代码评审必须先提出具体意见，再修正现有代码并验证。问题不能只停留在报告里；不修、误报或待决策项必须写明理由。

```markdown
# 代码评审报告：<需求名称>

## 评审方式
（由评审 agent 执行，相当于同事工程师做 code review，主流程不自评；主流程逐条判定“已修复 / 不修 / 误报 / 待决策”，不采纳要写理由，判定结果同时记进 `编排记录.md` 的「评审判定」表；判为已修复的条目由同一个开发 agent 实例修正）

## 评审范围
（当前需求涉及的代码改动、调用方、接口、数据、文档和可测性；测试充分性由测试阶段把关；没有代码改动时写“不适用”及原因）

## 评审结论
（两三句话说明代码是否可进入验收、发现的问题数量和修正状态）

## 问题清单
| 编号 | 级别 | 位置 | 问题与风险 | 改进意见 | 处理决定 | 修正结果 | 验证证据 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| CR-1 | 阻断 / 应修 / 建议 | | | | 已修复 / 不修 / 待决策 / 误报 | | |

## 影响与后续测试
（修正是否影响业务逻辑、接口、数据或用户可见行为；影响时把受影响的**业务路径**（业务语言，不附 diff）写下来，交主流程转给测试阶段进必测清单，并在 `测试报告.md` 的「变更后补充测试」里留证据。改了代码的，记下重新构建的 debug 包版本）

## 复审结果
（阻断和应修项修完后，由同一个评审 agent 复审改动点的结论；没有就写“无”）

## 未修正项
（没有就写“无”；有则逐条写不修理由和后续建议）

## 范围外发现
| 编号 | 位置 | 现象 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| OOS-1 | | | | |

（只记录不修改：与本次需求无关的既有 bug 和体验问题，哪怕就在本次改动的文件里也不顺手修，留给用户决定是否另开需求；没有就写“无”）

## 结论
（已闭环，可进入验收 / 存在待决策项，不可进入验收）
```

## 准出检查清单：代码评审 → 测试
- 评审由评审 agent（相当于同事工程师）执行，范围覆盖本次改动的调用方、接口、数据和可测性
- 评审 agent 没有跑构建或测试，也没有写代码
- 主流程对每条意见给出判定，不采纳、误报、待决策的都写了理由，判定已记进编排记录
- 阻挡项和应修项由**开发 agent**（同一个实例）修复，修复结果写进「修正结果」
- 阻断项和应修项已修复，并由同一个评审 agent 复审改动点
- 修正影响业务逻辑的，已把受影响业务路径写成业务语言清单，交主流程转给测试阶段进必测清单
- 不影响业务逻辑的修正已完成对应编译、静态检查或相关测试（由开发 agent 跑并写进回执）
- 范围外的问题只记录，已列进「范围外发现」，没有顺手改动
- 未闭环的阻断项为 0，才允许请求用户批准

（主流程校验通过才能进入阶段 6（测试）；不达标把缺口清单发回对应 agent 返工。）
