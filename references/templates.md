# 产出模板与准出检查清单

按当前阶段取用对应模板。**用户主动调用 `$requirement-spec` 时，必须完整使用产品需求、设计、技术方案、代码评审、测试和验收模板，不判 S / M / L，也不按档位裁剪。** 只有 AI 自动调用时才按变更范围、数据与契约、风险、不确定度、验证成本五个维度取最高档判规模：S 级需求通常只用产品需求、代码评审报告和验收文档，M 级通常用到产品需求、设计说明、代码评审报告和验收文档；自动调用发现新风险后必须即时升级规模并补齐产物。占位内容一律替换成真实内容，模板里的空标题不要留在最终产出里。

## 产品需求（阶段 1）

该阶段同时产出需求卡片和 PRD。开始写文档前，先把答案会改变范围、验收标准、架构、数据契约或用户可见行为的疑点全部问清楚，数量不限；只影响实现细节的问题按推荐默认值写进“采用假设”。

## 各阶段准出检查清单

进入下一阶段前快速过一遍，不达标就补，不要带着缺口往下走。

**产品需求 → 设计**
- 会改变范围、验收或架构的疑点已全部提问并记录回答，其余按“采用假设”记录
- 目标、范围、明确不做的事、验收标准四样齐全
- 假设逐条有依据，待确认项已经问过或已转成假设
- 规模一栏已填：用户主动调用时写“不分级（强制全流程）”且没有按档位裁剪产物；AI 自动调用时 S / M / L 有分级理由
- 该阶段未修改项目下任何文件
- 每条验收标准都能对应到功能清单
- 功能清单每条有 REQ 编号，验收标准每条有 AC 编号并标注覆盖的 REQ
- 歧义扫描已完成，互相矛盾、无法判定、缺边界、悬空引用四类都处理过
- 异常和边界写到了，没有“出错时提示一下”这类模糊表述
- 非功能需求（性能、兼容、多语言、权限）有明确结论或写明不涉及
- 监测指标定义齐全，每条指标都能对应到具体的日志或埋点

**设计 → 技术方案**
- 任务开始前就跑过 `assets/figma-auth.js check`，结果是可用（exit 0）；中途重新授权过的话，新 token 也验证通过；账号/计划/席位已记进需求卡片的环境信息
- 正常态、空态、超长文案、极端数据都有稿；加载态和错误态已给出保留或舍弃的判断和理由
- `design-spec.json` 存在且是设计源，`html/`、PNG、按需的 `use-figma.js` 都由自带的渲染/截图/编译脚本从它派生，没有手写 Figma 代码或 HTML 充当设计源的痕迹
- 老页面用的是截图库里最新的真实截图，改动区域在 spec 里重建了图层且出稿范围标为“改动区域”；新页面或库里缺图的页面标为“整页”
