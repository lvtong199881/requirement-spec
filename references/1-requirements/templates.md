# 阶段 1 模板与准出清单

本阶段产出产品需求相关文档，由**需求 agent** 产出。模板里的占位内容一律替换成真实内容，空标题不要留在最终产出里。

## 待提问清单（随回执交回主流程）

```markdown
# 待提问清单：<需求名称>

只列答案会改变范围、验收标准、架构、数据契约或用户可见行为的疑点。没有就写“无”。
只影响实现细节的不进这张表，直接写成采用假设。

| 编号 | 问题 | 会改变什么 | 推荐答案 |
| --- | --- | --- | --- |
| Q-1 | | 范围 / 验收标准 / 架构 / 数据契约 / 用户可见行为 | |
```

主流程拿这张表向用户逐条提问，把回答 `send_message` 发回同一个需求 agent，由它并入 PRD 的「澄清问题」表。

## 文档模板

该阶段同时产出需求卡片和 PRD。开始写文档前，先把答案会改变范围、验收标准、架构、数据契约或用户可见行为的疑点全部问清楚，数量不限；只影响实现细节的问题按推荐默认值写进“采用假设”。

- 环境：Figma 账号 / 计划 / 席位（任务开始前 `figma-auth.js check` 的输出）；本需求将建的文件名 `<工作区名> / <需求标识>`

## 准出检查清单：产品需求 → 设计
- 文档由需求 agent（独立子 agent）产出，不是主流程代写
- 会改变范围、验收或架构的疑点已全部进「待提问清单」，主流程已提问并回填回答；其余按“采用假设”记录
- 目标、范围、明确不做的事、验收标准四样齐全
- 假设逐条有依据，待确认项已经问过或已转成假设
- 规模一栏已填：用户主动调用时写“不分级（强制全流程）”且没有按档位裁剪产物；AI 自动调用时 S / M / L 有分级理由
- 该阶段未修改项目下任何源码、配置、资源或测试（需求文档落盘属交接介质，不算违规）
- 每条验收标准都能对应到功能清单
- 功能清单每条有 REQ 编号，验收标准每条有 AC 编号并标注覆盖的 REQ
- 歧义扫描已完成，互相矛盾、无法判定、缺边界、悬空引用四类都处理过
- 异常和边界写到了，没有“出错时提示一下”这类模糊表述
- 非功能需求（性能、兼容、多语言、权限）有明确结论或写明不涉及
- 监测指标定义齐全，每条指标都能对应到具体的日志或埋点

（主流程校验通过后才能进入阶段 2（设计）；不达标把缺口清单发回同一个需求 agent 返工。）
